# Known Limitations — Sprint 4

Зафиксированные ограничения и технический долг по итогам Sprint 4.

---

## Мобильный клиент

### 1. Page Visibility API не реализован

**Описание:** `markRead` вызывается при открытии диалога и при получении `message_new`,
независимо от того, видима ли вкладка/приложение в данный момент.
В браузере и PWA сообщение считается «прочитанным» даже если вкладка свёрнута или скрыта.

**Риск:** TTL-отсчёт запускается на сообщениях, которые пользователь фактически не видел.

**Решение:** Sprint 5 — реализовать проверку `document.hidden` перед `markRead`
и обработчик `visibilitychange` для дочитывания непрочитанных при возврате фокуса.
Задача добавлена в `docs/sprint-5-checklist.md` (пункт 14).

---

### 2. Мобильный клиент использует `user_id` вместо логина/пароля

**Описание:** Экран Login принимает UUID пользователя напрямую без пароля (dev-режим).

**Риск:** Не подходит для продакшн.

**Решение:** Sprint 6 — добавить реальную аутентификацию (login/password).

---

### 3. Биометрическая аутентификация не работает в браузере

**Описание:** `@aparajita/capacitor-biometric-auth` возвращает `User cancelled`
в браузере (не Capacitor). Реализован fallback `startUnlockNoBiometric`,
который использует refresh-токен напрямую.

**Риск:** При запуске в Capacitor на устройстве без биометрики поведение не тестировалось.

**Решение:** Добавить обработку `BiometryErrorType.biometryNotEnrolled` и устройство-специфичный fallback.

---

## Серверная часть

### 4. `message_deleted` не доставляется оффлайн-пользователям

**Описание:** `ws_event_outbox` обрабатывается только для онлайн-пользователей.
Если пользователь был оффлайн в момент истечения TTL, он не получит `message_deleted`.
При reconnect `ListMessages` вернёт пустой список (soft-delete фильтр), — это корректно.
Однако badge-счётчик непрочитанных может не обновиться.

**Риск:** Незначительный — пользователь не видит удалённое сообщение, но badge может остаться.

**Решение:** При reconnect добавить пересчёт unread-badge через `GET /api/v1/unread` (Sprint 5+).

**Смягчено (2026-08-14):** PWA при resume и WS reconnect перечитывает историю чата (`loadChatHistory`) и список на Home; истёкшие пузыри скрываются локально по `expires_at`, не только по `message_deleted`. Badge по-прежнему зависит от `GET unread` / `badge_updated`.

---

### 5. WS reconnect не запрашивает пропущенные события

**Описание:** При повторном подключении клиент заново грузит `ListMessages`,
но не знает, какие WS-события были пропущены (нет event sequence / cursor).

**Риск:** Если за время оффлайна пришли `message_ttl_started` или другие события —
клиент не узнает о них без обновления страницы.

**Решение:** При reconnect выполнять полный reload истории диалога (текущий подход — частичная компенсация). Полноценный event log — Sprint 6+.

**Смягчено (2026-08-14):** клиент делает полный reload ленты на WS `open` (если чат открыт и UI не locked) и на `visibilitychange` / PIN-unlock. Event log по-прежнему нет.

---

### 6. GitHub Actions CI не верифицирован на `main`-ветке

**Описание:** Workflow `.github/workflows/ci.yml` создан и проверен локально
(`task lint` — 0 issues, `task test` + `task test:integration` — все PASS).
Фактический прогон на GitHub не подтверждён (ветка не была запушена с тегом).

**Риск:** Возможны расхождения в окружении GitHub Actions (версии Go, зависимости).

**Решение:** При первом push на `main` убедиться, что все 4 jobs (lint/test/test-integration/build) зелёные.

## Инфраструктура

### 7. Нет device binding для refresh-токена (перенос из Sprint 3)

**Описание:** `AuthSession.DeviceID` сохраняется, но не проверяется при Refresh и Logout.

**Решение:** Sprint 6+.

---

### 8. JWT secret в конфиг-файле открытым текстом (перенос из Sprint 3)

**Описание:** `jwt.secret` хранится в YAML-конфигах, не зашифрован.

**Решение:** Перейти на vault / environment secrets при продакшн-деплое (Sprint 5 secrets management).

---

### 9. TTL — только глобальный конфиг, без гранулярности per-dialog

**Описание:** `chat.message_ttl_seconds` — один параметр для всех диалогов.
Нет возможности задать TTL per-message или per-dialog.

**Риск:** Низкий на текущем MVP-этапе.

**Решение:** Sprint 6+ — добавить `ttl_seconds` в тело `POST /api/v1/dialogs/{id}/messages`.
